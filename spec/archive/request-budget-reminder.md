# 请求预算提醒：用掉一半、四分之三时各提醒一次，只做交给你的部分

状态：已实现并验收（2026-10-29，tern 实现，Claude Code review、真实模型验收与评测对比）。

## 1. 为什么要改

编码评测 `spec-thread-goal`（照 spec 实现一份设计）前后 9 个整题试次里（含两次试改提示词的），代码每次都做对了、校验都通过，但有 6 次用满 120 次模型请求，按规则记为未通过。轨迹都一样：spec 里“tern 自己做”的验收（gofmt、vet、build、`node --check`）做完之后，接着几十轮去做 spec 写明归“Claude Code 在沙箱外做”的验收：起 app-server、写桩网页服务、开无头 Chrome 截图。

试过的改法（数据在 [harness-next-phase.md](../harness-next-phase.md) 第 5 节）：

| 改法 | 结果 |
| --- | --- |
| 在系统提示词的工作区规则里加一句“只做交给你的部分，写明归别人的即使做得到也不做” | 整题 k=3：3 次都用满 120 次，没有效果 |
| 同一句话作为提醒插在第 77 轮（回放） | 3/3 在 6–8 轮内收尾，都通过校验；插“继续。”的对照 0/3 |

同一句话放在开头（之后又堆了十几万上下文）不起作用，放在要做决定的时候起作用。而模型现在并不知道自己的请求预算：`max_steps` 只在 harness 里计数，用满时直接停下，连最终回答都没有。

所以由 harness 在预算用到 50%、75% 时各插一次提醒：告诉模型用了多少、用完会直接停，并提醒只做交给它的部分。做法照搬已有的上下文用量提醒（`internal/agent/context_manager.go` 的 `remindUsage`：越过 50%、75% 各发一次，档位存在 `State.Announced`）。

## 2. 改什么

1. **什么时候发**：每一轮请求模型之前（`internal/agent/react.go` 主循环里，和 `workspace.Reminders()` 的提醒放在一起、在它之后），算 `client.Calls`（已用的模型请求，含摘要）占 `maxSteps` 的比例。越过 50%、75% 的档位时各发一次，同一档不重复发；一次越过两档（比如续跑时）只发高的那一档。`maxSteps` 是不限（`llm.Unlimited`）时不发。`-max-steps` 默认是 0（不限），所以只有设了上限的运行（评测题、手动指定）会有这条提醒。
2. **发什么**（一条 `llm.Reminder`）：

   ```
   [请求预算] 已用 {已用} / {上限} 次模型请求（含摘要）。用完会直接停下，没有机会再给最终回答。只做任务交给你的部分：任务或文档写明由别人做的检查，即使这里做得到也不要做；自己那部分做完就给最终回答，没做的列出来。
   ```

   终端日志打一行 `Budget reminder: level=50 calls=60 max=120`（和 `Context reminder` 的写法一致）。
3. **档位存哪**：`State` 加一个字段 `Budget int`（JSON `budget,omitempty`），注释写“已经提醒过的请求预算档位（50、75）”。
   - **续跑**（`resume != nil`）：接着用检查点里的档位，因为预算跨续跑累计（`client.Calls` 也是接着的）。
   - **续聊**（`history != nil`）：每一轮的预算从 0 重新算，档位也从 0 开始，**不**继承上一轮的。注意现在续聊时 `state` 取自上一轮检查点，`Env`、`Announced` 是接着用的；`Budget` 不能跟着它们一起接。
   - **压缩**：不清零。压缩不改变已用的请求数。
   - 回放分叉（`ForkCheckpoint`/`ForkSnapshot`）的 `State` 只继承私有来源，档位自然从 0 开始，不用改。
4. 子 agent 走同一个 `Run`，用自己的 `maxSteps`，不需要另外处理。

## 3. 按文件的改动

| 文件 | 改动 |
| --- | --- |
| `internal/agent/checkpoint.go` | `State` 加 `Budget int` 字段和注释。不改 `CheckpointVersion`（只是加了一个可以缺省的字段）。 |
| `internal/agent/react.go` | 主循环里请求模型前判断档位、发提醒、打日志；续跑时从 `state.Budget` 恢复，续聊时从 0 开始；保存检查点时把档位写进 `cp.State`（和 `Announced` 写在同一处）。判断档位写成一个小函数，和 `remindUsage` 放在一起或紧挨着主循环都可以。 |
| `internal/agent/AGENTS.md` | 如果里面有列 harness 会插哪些提醒的地方，补一行；没有就不加。 |

## 4. 这一期不做

- 不改默认的 `max_steps`，不加按 token 计的预算。
- 不改系统提示词。上面的数据说明放在开头没用。
- 不做“检测到在沙箱外起服务就提醒”这类按行为判断的触发，等这一版的数据出来再说。
- 网页端不显示这条提醒，它和其他 harness 提醒一样只进模型上下文。

## 5. 验收

### tern 自己做（不需要真实模型，在沙箱里）

1. `gofmt -l .` 没有输出；`go vet ./...`、`go build ./...` 通过。
2. 读代码报告：上限 120 时，第几次请求前发第一条、第几次发第二条（按“已用次数越过档位”算，应该是第 61、91 次请求前）；续跑、续聊、压缩时档位分别怎么处理。

### Claude Code 在沙箱外做（真实模型，临时 `TERN_HOME`）

3. `-max-steps 8` 跑一个要多步的小任务：用掉 4 次后（第 5 次请求前）有 50% 的提醒，用掉 6 次后（第 7 次请求前）有 75% 的提醒，各一次；日志有两行 `Budget reminder`。
4. 续聊同一条对话：新一轮重新从 0 计，到 50% 又提醒一次。
5. 编码评测：5 道“照 spec 实现”的题 k=3（DeepSeek），和 `main@01eb8a8` 的基线比。看三个数：通过率、用满 120 次的次数、每试次请求数；另外抽看几条轨迹，确认 agent 自己的协议级自测（起 app-server 走协议）没有被一起压掉。

## 6. 实现与验收记录（2026-10-29）

- **实现**：tern（DeepSeek，网页端发任务）按第 3 节改了 `checkpoint.go`（`State.Budget`）、`context_manager.go`（`budgetLevel`，挨着 `remindUsage`）、`react.go`（续跑取检查点档位、续聊从 0、`save` 写回、主循环发提醒）。`internal/agent/AGENTS.md` 里没有列提醒的地方，按 spec 没改。网页端的平台设置关了 bash，这次 tern 没有 bash，第 1 条由 Claude Code 在外面跑。
- **review**：和 spec 一致。`main.go` 把 `-max-steps 0` 换成 `llm.Unlimited` 后才调 `agent.Run`（唯一的调用处），不限时不会误发。tern 的读代码报告另外指出：进程死在“发了提醒、还没存检查点”之间，续跑会再发一次同一档，最多一条重复，可以接受。
- **验收 1**：gofmt、vet、build、macOS 交叉编译通过。
- **验收 2**：tern 报告上限 120 时第 61、91 次请求前各发一次，与代码一致。
- **验收 3**（真实 DeepSeek，临时 `TERN_HOME`，`-max-steps 8`，6 个文件逐个读）：用掉 4 次后、用掉 6 次后各一条 `Budget reminder`，检查点里两条 `[请求预算]`；第 7 次请求给了最终回答。
- **验收 4**（app-server，平台设置 `max_steps=6`，同一条对话两轮）：第 1 轮用掉 3 次后提醒一次；第 2 轮（续聊）从 1/6 重新数，用掉 3 次后又提醒一次。
- **回放**（`e20261029-151338` 的 w-3 第 77 轮插入这条提醒的原文）：3/3 在 2–17 轮内收尾，都通过校验。
- **评测对比（验收 5，DeepSeek，5 道“照 spec 实现”的题 k=3）**：基线 `e20261029-182041`（`main@01eb8a8`），加提醒后 `e20261029-191533`。

  | 通过 | 11/15 | **15/15** |
  | 用满请求上限 | 3 | **0** |
