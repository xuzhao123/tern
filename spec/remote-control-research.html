Claude Code 与 Codex 的远程用法

远程 agent 的设计（remote-agent-design.md）写到一半发现需求没聊清楚：用户到底打开服务器上的网页，还是本机的 127.0.0.1？这一页整理 Claude Code 的 Remote Control 和 Codex 的远程连接、app-server 是怎么做的，再和 tern 的设计对照，最后列出要先对齐的产品问题。

界面都不是本机网页
要么是本机应用（终端、桌面端），要么是厂商托管的网页和手机 App。
配置以执行端为准
沙箱、权限、MCP、工具都用执行那台机器的；远程那一端只发消息、点审批。
模型由执行端调
用用户自己的账号，因为两家本身就是模型供应商。tern 做不到，只能由服务器代理、加密钥。

01为什么调研

设计稿第 1 节写“思路同 Claude Code 的 Remote Control”，同时要求“模型密钥只在服务器上”。核对下来，这里其实混着两个需求：

  • 用户不用自己的模型密钥：只要这一条，本机跑网页端、服务器只当模型代理就够了。
  • 在网页上操作本机代码：人在服务器的网页上（或换一台设备）看和审批，执行在用户本机。只有这一条才需要 Remote Control 那一套：控制连接、消息转发、断线补齐。

两家的做法能帮我们判断该要哪一个、哪些细节值得照搬。

Remote Control 细节

  • 三种启动方式：
    • claude remote-control 是服务模式：在项目目录里跑，一个进程同时服务多条会话（默认最多 32 条）。--spawn same-dir|worktree|session 决定并发会话共用目录、各用一个 git worktree，还是只服务一条。
    • claude --remote-control 是交互模式：终端和网页都能打字。
    • 已经开着的会话里输入 /remote-control，把当前对话接出去。
  • 配对：不粘令牌。CLI 先用 claude.ai 账号登录，会话只出现在这个账号的网页和 App 里；终端显示会话链接和二维码。第一次用要确认一次，没信任过的目录也要先确认。API key 登录不能用 Remote Control。
  • 连接：本机只发出站 HTTPS，不开端口。注册到 Anthropic 后轮询任务，服务器在网页和本机会话之间转发消息。凭证有好几个，都是短期的，各管一件事。
  • 配置以本机为准：文件系统、MCP、工具、项目配置都用本机的。权限模式在启动时用 --permission-mode 给，沙箱靠本机设置文件打开。写在 remote-control 前面的全局参数不会带给它起的会话，除非确认不影响会话能做什么，否则直接拒绝启动。网页上能换的是模型和推理强度。
  • 审批：权限请求和提问转发到网页或手机，一直等到人回答；可以配手机推送，在需要决定或任务完成时通知。
  • 存储：连着期间，完整对话（消息、回答、工具活动）存在 Anthropic 服务器上，用于多设备同步和断线重连。执行和文件留在本机。
  • 断线：
    • 笔记本睡眠或断网后自动重连。服务模式断网大约 10 分钟后放弃、进程退出；交互模式一直重试。
    • 停掉服务后大约 4 小时内，可以用 --continue 或 --session-id 接回。
    • 服务模式下某条会话崩溃了，从网页发一条消息就会重新拉起。
  • 网页上的额外功能：git 仓库有 diff 面板；附图直接给模型，其他附件下载到本机、按文件引用交给模型。
  • 管理：Team、Enterprise 要管理员打开开关。可选 Trusted Devices：用来操作的浏览器、手机要先登记，登录超过 18 小时要用指纹、面容或通行密钥确认一次。

04Codex

远程连接：手机或另一台电脑控制主机

  • 配对：在主机的 ChatGPT 桌面端打开 设置 → Connections → Control this Mac or PC，屏幕上出二维码；手机扫码后确认是同一账号、同一工作区，再过一遍多因素验证。每台手机要和每台主机分别配对。工作区管理员可能要先打开 Remote Control。
  • 连接：流量走 OpenAI 的“安全中继”，主机不暴露在公网上。文档没写中继存不存对话记录。
  • 手机上能做的：在主机的项目里开新对话或接着聊、插话、回答提问、审批；看 diff、测试结果、终端输出和截图；收通知；在几台主机之间切换。
  • 配置以主机为准：沙箱、审批规则、项目、凭证、插件、本机工具都用主机的。
  • 交接：一条对话可以连同 git 状态在本机和主机之间搬，两边都要有同一个仓库的项目；正在跑的对话会先被中断。
  • 限制：主机目前要求 macOS 或 Windows 上的桌面端，并且保持开机、联网、登录；睡眠或断网就连不上。

05协议层：Codex app-server 与 tern 的 app-server

tern 的协议注释写着“参考 Codex app-server”（internal/protocol/protocol.go），但两者对“对话归谁管”的处理不一样。

Codex app-servertern
进程长期运行；一个进程服务多条对话，多个界面可以同时订阅同一条；没人订阅 30 分钟后卸载一个进程只跑一轮，续聊时重新起进程
对话归谁归 app-server：本机 JSONL 文件加 SQLite 元数据；thread/start、thread/resume、thread/fork、thread/list、thread/deleteagent 里没有“对话”：历史在网页端存档里，续聊时放进 turn/start 传给新进程；检查点在 agent 那边
单位thread（对话）› turn（一问加随后的工作）› item（消息、命令、改文件、工具调用）turn 与 item；对话由网页端拼起来
传输stdio（默认）；WebSocket（实验性，鉴权用能力令牌或签名令牌，带 Origin 头的请求一律拒绝）；Unix socket 上跑 WebSocketstdio；Unix socket 上一行一条 JSON
握手与断线先 initialize；断线后 thread/resume，再分页读历史session/attach {token, after}，按序号补发漏掉的消息；没人连着最多等 10 分钟
插话与停止turn/steer（要带 expectedTurnId）、turn/interruptturn/steer、turn/interrupt
审批与提问item/commandExecution/requestApproval、item/fileChange/requestApproval（回 accept、acceptForSession、decline、cancel）；item/permissions/requestApproval（网络与文件权限，可按轮或按会话给）；tool/requestUserInput；mcpServer/elicitation/requesttool/requestApproval（可回 allow_session）、network/requestApproval、user/requestInput
账号与模型account/login/start：ChatGPT 网页登录、设备码、API key；模型由 app-server 自己调没有账号接口；模型请求经网页端代理（AGENT_PROXY_URL），或用本机 .env 的密钥
配置config/read、config/value/write 读写本机 config.toml；管理员限制在 requirements.toml全靠启动参数，由界面决定（网页端把设置拍成快照传进来）

最大的区别：Codex 的对话归执行端管，tern 的对话归界面（网页端）管，agent 只是一次一轮的执行者。本机跑网页端时这没有问题；把执行端搬到用户机器、界面留在服务器上时，续聊要从服务器存档还原，检查点却在用户本机，断线重连要两边配合。设计稿里很多复杂度都从这里来。

设计稿里的 tern connect（方案 A）Remote Control 服务模式远程连接的主机端
方案 B桌面端 Local 会话，再加上用账号调模型桌面端本机项目，再加上用 ChatGPT 账号

所以“本机跑完 connect、打开 127.0.0.1”在两家那里对应的不是 Remote Control，而是桌面端的本机会话。两家的桌面端都是原生应用，不是浏览器开本机端口；tern 的本机网页端在这里的位置相当于它们的桌面端。

08共同点，以及对 tern 的含义

  1. 都没有“本机打开网页”这种形态。本机用原生应用，远程用厂商托管的网页和手机 App。
  2. 配对都靠账号登录或短期有效的码，不用长期令牌。
  3. 配置、权限、沙箱都以执行端为准。远程那一端只发消息、点审批。设计稿反过来以服务器设置为准，所以第 8 节要写一整套“本机过滤服务器下发的东西”。
  4. 模型请求都由执行端自己发，用用户自己的账号，因为两家就是模型供应商。tern 用方舟和 DeepSeek，没法给每个用户发短期凭证，所以由服务器代理、服务器加密钥。这是 tern 和两家根本不同的地方，无论选 A 还是 B 都要做。
  5. 本机那一侧都是长期运行的（Codex 的 app-server 守护进程、Claude 的服务模式），对话归本机进程管。tern 是界面管对话、agent 一次一轮。

09要先对齐的产品问题

  1. Q1

    给谁用、什么场景？

    • 你自己：在电脑上干活，离开时用手机或别的电脑看进度、点审批。
    • 团队或租户：你部署一个 tern web，大家用自己电脑上的代码，用你的模型额度。
    • 只是不想让用户自己配模型密钥。

    先定。只要最后一条，方案 B 就够了。

  2. Q2

    人主要在哪看、在哪点审批？本机浏览器、服务器上的网页（换设备也能看），还是手机？

    先定。要换设备或手机，只能走方案 A，或者先做 B、以后再加 A。

  3. Q3

    服务器要提供哪些东西？模型额度、账号、对话存档和多设备同步、统一的设置、审批入口。

  4. Q4

    配置以谁为准？像两家一样以本机为准，还是保留以服务器设置为准（像现在的 tern web）？

    决定设计稿第 8 节安全边界怎么写。

  5. Q5

    对话归谁管？继续由网页端管（服务器存档、agent 一次一轮），还是像 Codex 那样归本机（本机存对话，服务器只转发和显示）？

    影响最大，牵涉到 tern 现有的协议要不要改。

  6. Q6

    本机终端要不要也能参与同一条对话？像 claude --remote-control 那样两边都能打字，还是只显示日志？

  7. Q7

    配对方式：粘贴长期令牌，还是浏览器登录授权或短期配对码？
