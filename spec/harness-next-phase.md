## 3. 流程上的调整

上一批的问题不在代码质量，而在一次改得太多、太久没提交、验收和实现混在一起。建议：

1. **一份 spec 一个分支，做完就合**：不在一个分支上攒一周的改动。单次合并控制在几百到一两千行，超过就拆 spec。
2. **实现者回到 tern**：按 tern-implement 的流程，让 tern（DeepSeek）照 spec 做，Claude Code 对照 spec review。这本身也是对 harness 最真实的测试，做不好的地方就是第 1 期的改进素材。需要别的模型帮忙时，同样从 spec 出发，同样走 review。
3. **验收脚本和评测分开**：`spec/web-product/check-*` 是产品功能的验收，评测集量的是 agent 的能力，两者都要有，但不互相替代。
4. **合并前固定检查**：gofmt、vet、build、macOS 交叉编译、`node --check`，跑编码评测和基线比，前端改动在浏览器里至少点一遍主流程。
