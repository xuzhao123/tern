# 当前轮补充：服务端所有权、采纳回执与下一轮仲裁

状态：开发中。对应 CHAT-02/03/05、A08/A09/A11/A12，与 13 的下一轮队列共用调度；旧版 chat 的协议行为保持兼容。

## 契约

- 新网页显式使用 managed=true，携带 request_id/client_id 与目标 turn_seq。先持久保存再确认接收；确认接收不等于模型已采纳。错轮次拒绝并保留草稿，不偷偷插到另一轮。
- 同 ID 同内容在 agent 端去重，不同内容拒绝。新增 turn/steer/status 查询接收/采纳结果；未知响应先查询，不靠重复文字猜测。旧运行实例不支持该能力时不向它盲重发，显示延至下一轮。
- managed 补充的采纳 ID/内容哈希/结果进入检查点 state，检查点格式升级至 3，旧版本默认为无回执。先将有效上下文和回执保存，再发采纳通知。采纳表示进入有效上下文，不表示任务已完成。
- UserPromptSubmit 拦截后只记录 blocked 和安全占位，不把原文转成下一轮。持久待发区在处理前会暂存原文（0600），拦截确认后清除；请求回执只保存 ID/状态，不复制原文。旧存档和旧调用仍可读。
- 未采纳补充转入新轮时，启动事件只记录来源补充 ID 和待核对占位；原文经 turn/start 交给 agent。提交规则通过后的 userMessage / 模型请求才可携带原文；若新轮被拦截，来源补充转为 blocked。重启从该轮事件和检查点恢复此结果，不能因转成队列而失去拦截语义。
- 正常轮次结束后，明确未采纳的 managed 补充按接收顺序合并成下一轮的一项，排在普通 follow-up 队列前，服务端只转交一次。旧 chat/旧网页的 unmanaged queued 字符串仍由旧客户端处理，不混用两个所有者。
- 停止时未采纳补充保留到暂停队列。立即发送显式指定补充 ID，先停止当前轮，核对实际采纳结果后只发送仍未采纳的一组；普通队列保持暂停。已经采纳的内容不重发。
- 非正常退出且没有采纳或未采纳证据时标 unknown，保留文本供核对，不自动重做。用户可明确转入暂停队列或移除；状态竞争拒绝，不取消仍可能被当前 agent 采纳的消息。
- 页面显示同一份服务端待采纳状态；刷新和切换页面不创建新发送。旧版浏览器本地残留只允许核对后恢复为草稿，不能自动迁移成一次执行。
- 补充状态写盘失败时，页面显示保存失败并保留原状态；未完成核对前不派发后续队列。修复存储后可“核对状态”，依据原回执/检查点恢复，不能因保存失败重发已采纳内容。“停止并发送”只请求正常停止，即使在停止过程中增加新的补充，也不能升级成强制结束；强制结束仍是独立的人为操作。

### 转交后的提交确认与原文恢复

真实复现发现：转交文本以不存在的斜杠命令开头时，agent 在 UserPromptSubmit 前退出；只有 continue 启动记录不能证明输入已提交。原实现此时清除 claim 并标 delivered，导致待发原文无法找回。修复使用现有 queue_claim 保存转交中的输入，不另建持久输入表。

- managed fallback 领取后，queue_claim 保留原文与 steer_ids，直到关联轮次出现规则通过后的非 steer userMessage、真实主模型请求，或检查点中的实际模型调用证据；这些证据表示输入已被接收，届时清除 claim、将来源记录标 delivered。正常 exit 本身不算提交确认。
- 明确 hook_blocked 时清除 claim 原文，来源记录转 blocked；continue 和 trace 的启动文本继续使用安全占位，受拦原文不能通过回执副本再次留下。queue/send 成功及 pending 回查只返回任务 ID/队列 ID，不把 claim 或队列正文复制进持久回执。
- 已有 queue_id 但没有上述提交证据时，运行中继续等待；轮次结束后持久暂停队列并保留 claim 原文，显示“提交结果待核对”。失败和未知都不自动重发、不得仅凭 exit 标 delivered。启动前验证失败仍按原契约放回待发并暂停。
- 页面允许把此 claim 复制/恢复到当前输入草稿，保留原有草稿文字与附件，不直接发送。用户核对历史后可明确释放领取项；释放清除 claim，来源记录进入 released（区别于普通移除/确认拦截的 discarded），队列保持暂停，不创建新轮次。需要再执行时由用户以新请求主动发送草稿。
- managed continue 记录转交前的 `resume_from` 检查点身份。提交前失败可能只打印新检查点 ID、尚未写出文件；只有用户明确释放该领取项后，且该新检查点确实缺失，后续主动发送才允许沿已记录的前序检查点恢复上下文。存在但不可读/损坏的检查点不能据此跳过；不会自动执行，也不撤销磁盘文件。
- `thread/queue/recover` / `POST /runs/{id}/queue/recover` 的无 action 请求仍只核对证据；新增 `action=release` 必须携带对应 claim id 与最新 version。仅允许释放已结束且没有提交/拦截证据的 managed claim；运行中、过期版本、错误 ID 或已确认状态返回 409。旧客户端与普通队列的恢复语义保持不变。

验收：真实 ask_user 等待期间补充一个不存在的斜杠命令并停止转交，确认仅新增一次 continue、原文仍在 claim、不会自动重做；重启后保持。核对接口无证据不得清除，错误版本/运行中释放拒绝。浏览器恢复草稿不覆盖已有输入，明确释放后原文不再待发、普通队列仍暂停、没有新 continue；随后新请求可正常执行。自然转交/立即转交 hook 拦截和正常通过路径须回归，检查存档、检查点、协议会话与发送回执不存在受拦原文。

## 责任与边界

agent/interact.go 负责进程内去重与状态查询，react.go/checkpoint.go 负责有效上下文与采纳证据；appserver 的 .meta.json 保存传输状态，结合事件和检查点核对，再进入 queue.go；网页负责草稿、回执与呈现。新 managed 模式只用于文本；已有附件不能被静默丢弃。旧版客户端不声明 managed 时保留原方法语义。

## 验收

真实模型执行工具期间补充，多个客户端重复提交只采纳一次；应用服务重启后待发状态与 ID 不变；用户停止、立即发送、模型自然结束分别核对下一轮；目标轮次变化拒绝；hook 拦截不进入下一轮且待发原文清除；异常中断未知态不自动重发。对照实际模型请求、检查点与 queue_id，而不是只看 UI 标签。Go 格式/vet/build、JS 语法及真实浏览器验证；未覆盖的失败窗口不标已验收。
