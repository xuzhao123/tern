## 先读这里

下面记录 `main@6fba4ad` 的产品梳理基线，当前实现与已验证状态见 [08](08-implementation.md)。当时的主要问题是**功能按实现模块排列，尚未围绕一个任务形成连贯的工作界面**：工作区主要是输入框里的下拉项，设置、评测与审计占据侧栏上半部；改动、文件、子任务和浏览器没有统一的工作面板；运行、插话、队列、审批、断线和继续的状态分散在各处。

旧的 [Codex 对齐清单](../codex-parity-plan.md) 完成了其中定义的具体能力，不等于整个产品体验已经一致。例如：

| --- | --- |
| 按工作区筛选对话 | 不是可展开的项目树；改名后旧对话仍保留旧名 |
| 工作区 diff + `/review` 命令 | 不是可选择范围、有行号和反馈草稿的代码评审工作台 |
| 插话与服务端排队 | 缺少统一的发送状态；队列尚不能编辑和排序；主输入草稿无按任务持久化 |

| appclient 自动重连 | 浏览器事件流出错仍提示重新选择对话，不能等同端到端自动恢复 |

## 对齐的含义

参考对象是 **Codex 桌面端的编码任务体验**，交付载体是 Tern Web。核心语义与主要操作顺序尽量一致，布局适应浏览器；保留 Tern 名称、多供应商、SSH、沙箱、评测等现有能力。

1. 优先对齐用户能感知的结果：找得到任务、知道在哪里执行、知道是否在等自己、看得懂改了什么、离开后能回来继续。
2. 现有能力重排入口时，保持原有权限与执行语义。不能仅改标签就宣称支持切换模型、真 worktree、完整终端或全量撤销。
3. 日常界面只显示任务所需信息，原始请求、工具 JSON、审计与评测下沉到详情或开发者入口，仍可访问。
4. 对齐体验不承诺模型能力、速度、工具覆盖与 Codex 相同；这部分必须单独评估。
5. 本方案的尺寸、组件、优先级是 **Tern 的设计建议**，并非测量得到的 Codex 精确规格。官方来源确认的是功能语义；尚未做 Codex 全量界面的逐像素比对。

## 推荐产品决策

以下是可供开发采用的默认方案，不冒充用户已经逐项确认的决定：

- 主导航按项目和任务组织；主机作为项目/任务的执行位置标签，多主机筛选保留。
- 产品主文案用「任务」「项目」「工作目录」「执行位置」，技术层仍保留 thread/turn/workspace，不为改名重写协议。
- 项目在第一版仍对应单台主机上的一个登记目录；无项目任务仍可使用。多目录项目留到后续。
- 一条任务可有多轮消息；本轮完成不等于整个任务永久完成，允许继续。
- 对话居中，右侧统一工作面板，默认按需打开；开发者观测不再和日常对话同级抢占主入口。
- 首版保留当前「Enter 补充当前轮、显式按钮排到下一轮」语义；Tab 恢复键盘焦点导航，排队改用可发现按钮和经浏览器冲突验证的快捷键。
- 首版模型仍按任务固定，但要清晰解释，并提供带上下文开启新任务的入口；真正每轮换模型属于 B5。
- 现有用户的权限值原样迁移；没有显式配置的新用户推荐「自动编辑」。权限与计划模式分开呈现前，不能把当前 `plan` 限制包装成新的完整规划协议。

需要进一步定稿的事项见 [04 的决策清单](04-delivery.md#尚待产品定稿的选择)。这些选择不阻止先讨论和开发不依赖它们的批次。

## 如何更新状态

新增需求统一为「未开始」。经过对应场景验收才改为「已验收」，并填写实现提交与证据。旧 spec 的「已实现」继续有效；新需求引用旧能力并补充新体验，不回滚旧状态。修改本方案影响已有功能语义时，先同步对应旧 spec，再实现。
