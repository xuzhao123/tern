# 下一轮队列：编辑、排序、原子领取与恢复

状态：开发中。对应 CHAT-02/05，验收 A08/A09/A12。当前轮 steer 的服务端持久化仍单独推进，不把本文件当成整个可靠发送已完成。

- 队列内容、顺序、版本、暂停标记与已领取项由 app-server 持久保存。每次成功队列修改递增 queue_version；编辑/排序必须带预期版本，冲突返回 409 并保留用户编辑草稿。排序必须是当前待发项 ID 的完整无重复排列。
- 元数据从读、校验、写盘到更新内存共用 r.mu 临界区，改名/目标/归档不能与队列更新互相覆盖；写入失败保留原状态。
- add 接受 request_id，复用普通发送回执；响应丢失先查询，不重复追加。队列项保留原提交者，自动续轮使用其身份。暂只排文本，已有附件不能被静默丢弃。
- 新增 thread/queue/update、reorder、send；web 对应 PUT /runs/{id}/queue/{qid}、PUT /runs/{id}/queue、POST /runs/{id}/queue/send。send 必须提供当前队首 ID 和预期版本，由服务端领取并启动，网页不再先 messages 再 DELETE。
- 领取前持久保存 queue_claim，同时从待发集合移出。普通续聊与队列领取串行；已领取项不能编辑、删除或排序。continue 事件持久记录 queue_id 后才起 agent，启动前记录写入失败不运行。
- managed 补充转交的 claim 要额外等待提交规则确认，不能仅凭 queue_id/exit 清除原文；提交前失败或未知保留 claim 并暂停，允许恢复草稿和明确释放，详见 [14](14-managed-steer.md)。无 action 的 recover 不自动重做；release 要校验 claim ID/队列版本并确认关联轮次已结束。queue/send 的持久回执只含任务 ID/queue_id，不复制仍待提交规则处理的 claim 原文。
- 重启核对 claim 与 queue_id：事件已存在则该项已经交给本轮，不再重新执行；无启动事件则恢复为待发并暂停，等用户明确操作。证据不完整/写盘失败时保留待确认状态，不自动重做。手动领取同时保存 dispatch_request_id/dispatch_user；确认未启动后把待确认发送回执终结为 rejected，用户可核对后用新请求发送，避免回执永远 pending。已有启动事件的 ID 即使残留在旧队列快照也会去重。
- “停止”先持久暂停后续队列再中断当前轮；重启不取消暂停。之后普通续聊不自动解锁队列。手动“发第一条”只消费一条；“继续全部”才解除暂停并顺序消费。只有本轮正常结束才自动取下一条，失败保留剩余项并给原因。
- 未修改的旧 meta 默认版本 0、无 claim、不暂停；旧客户端删除仍兼容，新增编辑/排序/发送必须校验版本。旧队列在升级重启后保持可见；不把升级本身当自动启动授权。
- 新队列（queue_version > 0）重启接管后按原暂停状态与上一轮实际结束证据恢复调度；正常结束且未暂停才续发。版本 0 的旧队列不因升级自动启动。当前轮补充先按 [14](14-managed-steer.md) 核对，再决定普通队列能否继续。
- 编辑弹窗显示原版本和最新队列状态；409 后不覆盖输入，用户可核对最新内容再明确提交。各页面观察同一服务端状态。操作结果未知时保留文字与查询入口。

实现落点：appserver/threads.go 元数据事务；新增 queue.go 领域操作；server.go 启动事件、串行启动与摘要；live.go/启动恢复；handle.go 与 web/server.go 路由；前端队列操作/编辑弹窗与发送回执复用。

验收使用隔离真实服务与模型：并发添加不丢项，重复 request_id 不加第二项；并发改/排序一个成功一个冲突；领取后编辑拒绝；停止+重启不续发；单条/全部的行为不同；事件 queue_id 与实际轮次一一对应；损坏/非法排列拒绝；浏览器双页编辑冲突保留草稿。Go 格式/vet/build、JS 语法与实际 UI 检查。未执行场景保留待验收。

启动事件已持久化后发生进程启动/执行失败，该项作为已尝试的轮次保留在历史，暂停剩余项，不自动重复执行它。元数据保存失败时仍优先响应停止，并在当前进程内暂停队列、显示暂停状态未能持久保存；磁盘故障下的完整恢复仍需单独验收。
